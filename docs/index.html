为什么需要它

大多数 Agent 框架从提示词出发，长成一堆辅助函数。做演示可以， 但当两个团队要用同一套运行时、各自的提示词与工具、各自的合规要求时，就散了。 这个项目从反方向开始。

01

补丁协议上下文

状态不是一个随手改的 dict。每次写入都是 apply(Patch(op, path, by, value))，由归属表裁决这个 by 能不能碰这个 path。补丁日志同时是轨迹、回放源、预写日志。

02

ExecCtx 是大动脉

principal、预算、截止时间、trace id、幂等键、审批、深度、取消信号 都在一个对象里流转。每个面拿到同样的事实，不用摸全局。

03

有界循环

六个终止条件与三层死锁检测。停不下来的循环不是运行时，是事故。

04

按生命周期三态分离

Context 活一个回合，Session 活一次对话，Memory 活一张保留矩阵， Knowledge 活版本。混在一起是 Agent 系统里最常见的架构错误。

05

处处 SPI，核心零依赖

核心运行时不 import 任何第三方。每个外部系统都在一个协议后面， 默认实现用标准库，成熟实现可选。requirements-core.txt 是空文件，这是设计。

06

单请求放大是威胁模型

节点数、预算、分页、指标基数、workflow 容量全部有界。 一个请求不该能吃掉无限资源。

架构

一条主线、四个资源面、两个保障面。治理面 fail-closed（判不出来就是拒绝）， 质量面 fail-open（评测器坏了不能拦住回合）。

快速开始

核心零第三方依赖，装完即跑。

# 克隆与最小安装（requirements-core.txt 是空文件，这是设计）
git clone https://github.com/XiaoBinGan/Turing_AgentRuntime.git
cd Turing_AgentRuntime
python3 -m venv .venv && .venv/bin/pip install -r requirements-core.txt

# 从最小示例开始：40 行，不需要 API key
.venv/bin/python examples/quickstart/01_minimal.py

# 审批流：T2 工具 → 挂起 → 三种结果
.venv/bin/python examples/quickstart/03_approval.py

# 11 个端到端场景 + 八道门禁
.venv/bin/python demo/run.py
./verify.sh

起步一个回合

curl -X POST localhost:8000/v1/turns \
  -d '{"goal":"api p99 is 3s, find the root cause",
       "principal":{"user_id":"u","tenant":"acme","roles":["sre"],
                    "scopes":["runtime:run","tool.read"]}}'

接一个扩展

# 扩展按点分路径发现，运行时不静态 import 应用层
